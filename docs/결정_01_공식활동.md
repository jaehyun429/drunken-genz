# 결정 01 — 공식 활동: 무엇을 넣고, 어떻게 찾고, 분야를 어떻게 추천하나

- 작성: 소윤, 2026-11-16
- 상태: **제안** (8장 표가 정해지면 "결정"으로 바꿈)
- 범위: 공식 활동 목록, `GET /activities/search`, `POST /activities`, 기록 2단계의 "활동명으로 찾은 추천" 분야

## 1. 무엇을 만들어야 하나

| 기능 | 요구사항 (출처) |
|---|---|
| 공식 활동 검색 | 2글자부터, 0.3초 기다렸다가, 최대 5개, `verified`만. **별칭·띄어쓰기 무시**. 초성은 나중 (CLAUDE.md 6장, API 명세 2부) |
| 결과의 기록 수 | `record_count`, 5 미만이면 `null` (API 명세 1.8) |
| 새 활동 등록 | 없으면 "새 활동 등록" → `pending` 저장, 내 기록에만 연결, 운영이 7일 안에 검수 (CLAUDE.md 6장) |
| 분야 추천 | 1단계에서 쓴 활동명을 보고 2단계에서 분야 9개 중 하나를 추천 (11/16 시안 REC-02). **방법은 소윤이 정함** (11/16) |

전제:
- 공식 활동 데이터는 처음엔 **비어 있다**. 외부 사이트 크롤링은 안 한다 (CLAUDE.md 13장)
- 사용자가 많지 않은 베타. 공식 활동은 많아야 수백 개
- 이미 있는 것: `official_activity` 테이블, 검색용 글자 함수 `activity_search_text()` + pg_trgm 인덱스 (PR #7), 재현 서버의 LLM 클라이언트(`app/llm/client.py`)와 임베딩 클라이언트(`app/embedding/client.py`)

공식 활동 목록이 하는 일:
1. **기록 1단계에서 이름을 골라 쓰게** 해서 같은 활동을 한 사람들의 기록이 같은 이름으로 묶임 (오타·줄임말 차이 없이)
2. **분야 추천**: 공식 활동에 분야를 저장해 두면 고르는 순간 정확한 분야를 추천 (6장)
3. **공개 카드**에 `official_activity: { name, verified }`로 나가고, 기록이 5개 넘으면 "이 활동 기록 12개" 같은 숫자를 보여줌

→ 검색이 아무리 좋아도 **목록이 나쁘면 못 찾는다**. 목록에 들어갈 활동은 **여러 사람이 같은 이름으로 참여하는 것**이어야 의미가 있다.

## 2. 공식 활동에 무엇을 넣고 무엇을 빼나 (제안)

| 넣음 | 이유 |
|---|---|
| 전국 단위 대외활동: 서포터즈, 기자단, 대학생 프로그램 (예: ○○ 대학생 서포터즈 12기) | 여러 학교 학생이 같은 이름으로 참여. 기수마다 반복 |
| 연합 동아리 (예: 멋쟁이사자처럼, SOPT, 인액터스) | 같은 이유. 가짜 경험 데이터에도 "멋쟁이사자처럼 13기"가 있음 |
| 큰 공모전·해커톤 (해마다 열리는 것) | 같은 이름으로 많은 사람이 참여 |
| 전국 단위 봉사·멘토링 프로그램 (예: 해외봉사단, 대학생 교육 멘토링 사업) | 같은 이유 |
| 큰 축제·행사의 스태프·자원활동 (예: ○○국제영화제 자원활동가) | 같은 이유 |

| 뺌 | 이유 |
|---|---|
| **아르바이트 가게 이름** | 여러 사람이 같은 이름으로 묶일 일이 거의 없음. 가게 이름 + 시기면 사람이 특정될 수 있음 |
| **교내 동아리·학생회·과 행사·수업** (예: "2026 과준위") | 학교 하나에만 있음. 이름에 학교가 들어가면 익명 처리(학교는 "서울 소재 대학"처럼 넓게)와 부딪힘 |
| 하루짜리 봉사, 작은 공모전 | 같은 이름으로 묶이는 사람이 너무 적음 |

**교내 활동은 어떻게 하나?** → 공식 활동 없이 **활동명을 직접 쓰면** 됨 (지금도 공식 활동 연결은 선택). 사용자가 "새 활동 등록"을 눌러도 검수에서 `verified`로 올리지 않고 본인 기록에만 연결된 채로 둠.
→ ⚠️ **기획 확인 필요 (지은)**: 교내 활동을 공식 활동에서 빼는 것, 검수 기준.

## 3. 공식 활동 데이터를 어디서 구하나 — 조사 결과

### 공개 API (11/16 웹 검색으로 확인. 신청 전에 공공데이터포털 상세 페이지에서 다시 확인)

| 출처 | 무엇이 있나 | 우리에게 맞나 |
|---|---|---|
| [행정안전부 봉사참여정보서비스 (1365 자원봉사)](https://data.go.kr/catalog/15157582/openapi.json) | 1365에 올라온 봉사 모집 정보. 검색어·기간·지역·분야로 조회 | **안 맞음.** 기관별 하루·한 달짜리 모집 공고 수천 건이라 "같은 이름으로 묶이는 활동"이 아님. 큰 봉사 프로그램 몇 개만 손으로 넣는 게 나음 |
| [한국고용정보원 온통청년 청년정책 API](https://www.data.go.kr/data/15143273/openapi.do) | 정부 청년정책 (정책명, 주관기관, 분류) | **거의 안 맞음.** 대부분 지원금·제도라 "직접 한 경험"이 아님. 청년 인턴 같은 일부만 해당 |
| 한국관광공사 TourAPI ([이용 안내](https://studygov.kr/blog/13071-tourism-info-service/)) | 전국 축제·행사 정보 | **조금 맞음.** 축제 이름은 있지만 "스태프·자원활동" 모집 정보는 아님. 큰 축제 몇 개만 손으로 넣는 게 나음 |
| 공공데이터포털 "공모전" | 일부 기관의 공모전 파일 데이터만 있음 ([예](https://data.go.kr/data/15134251/openapi.do)) | **안 맞음.** 전체 공모전 목록이 아님 |

### 네이버 검색 API

- **자동완성 API는 공식으로 없다.** 네이버 API 허브가 주는 것은 블로그·웹·뉴스·카페 등 검색 결과뿐 ([API 허브 안내](https://guide.ncloud-docs.com/docs/apihub-overview)). 자동완성 주소를 몰래 부르는 방법은 약관 위반·차단 위험
- **검색 결과를 우리 DB에 쌓을 수 없다.** 개정 약관은 검색 API를 "네이버 검색 결과를 보여주는 목적"으로만 쓰게 하고, 결과를 가공하거나 보관하는 것을 제한함. 서버 보관은 이력 조회 목적으로 최대 21일 ([보도](https://www.tokenpost.kr/news/ai/403521), [정리 글](https://brunch.co.kr/@ainote/123), [검색어 트렌드 API 문서](https://guide.ncloud-docs.com/docs/searchtrend-spec))
- 결과도 블로그·뉴스 **글 제목**이라 "멋쟁이사자처럼 13기" 같은 깔끔한 활동 이름이 아님
- 호출 한도가 있음 (하루 2만 5천 회 또는 1천 회 — 출처마다 다름, 신청 때 확인). 글자 칠 때마다 부르면 금방 참
- → **쓸 수 있는 곳**: 검색 결과가 없을 때 "네이버에서 찾아보기" **링크**를 보여주는 정도. 데이터 출처로는 못 씀

### 대외활동 사이트 (링커리어, 위비티, 캠퍼스픽 등)

- 대학생 대외활동·공모전이 제일 많이 모인 곳이지만 **공개 API가 없다**. 개인 프로젝트들은 웹 페이지를 긁어 오는 방식을 쓰고 있음 ([예](https://github.com/kanggihoo/vps-info/issues/17))
- 링커리어 [이용약관](https://linkareer.com/terms/2025-12-23)에 **크롤링·스크래핑 같은 자동 수집 금지** 조항이 있음
- 비슷한 사건에서 **민사 손해배상이 인정된 적이 있음**: 잡코리아가 사람인 채용정보를 긁어 와 2억 5천만 원 배상 (데이터베이스 제작자 권리 침해), 여기어때가 야놀자 정보를 긁어 와 부정경쟁행위로 배상. 형사는 무죄가 나오기도 했지만 민사 책임은 남음 ([정리](https://www.innoforest.co.kr/report/NS00000366/), [대법원 2021도1533 분석](https://atlaw.kr/kr-blog/%EC%9B%B9%ED%81%AC%EB%A1%A4%EB%A7%81%EC%9D%98-%ED%98%95%EC%82%AC%EC%B2%98%EB%B2%8C-%EA%B0%80%EB%8A%A5%EC%84%B1-%EB%8C%80%EB%B2%95%EC%9B%90-2021%EB%8F%841533-%ED%8C%90%EA%B2%B0-%EC%99%84%EC%A0%84/))
- **할 수 있는 것**
  1. **사람이 보고 이름만 옮겨 적기**: 활동 이름·주최·기수는 사실 정보. 100개 안팎을 손으로 고르는 건 사이트 데이터를 통째로 베끼는 것과 다름. 설명글·이미지는 안 가져옴
  2. **제휴 문의**: 정식으로 데이터를 받는 유일한 길. 베타 일정엔 늦을 수 있지만 메일 한 통은 보내 볼 만함
  3. **링크만 걸기**: 검색 결과가 없을 때 "링커리어에서 찾아보기" 링크
- **하지 않을 것**: 자동으로 목록 긁어 오기, 숨은 API 부르기, 사용자가 붙인 공고 주소를 서버가 대신 열어 내용 뽑기 (한 장이라도 약관상 자동 수집으로 볼 수 있음)

### 우리 사용자가 쓴 활동명 모으기

- 사용자들이 공식 활동 없이 직접 쓴 활동명을 서버가 모아서, **서로 다른 사람 5명 이상이 같은 이름**(띄어쓰기·대소문자 무시)을 쓰면 검수 후보로 올림
- 장점: 외부 데이터가 필요 없음. 우리 사용자가 실제로 하는 활동만 쌓임. "5명 이상"이라 교내 활동처럼 사람이 특정되는 이름은 자연히 걸러짐 (익명 처리의 5명 기준과 같음)
- 단점: 사용자가 쌓여야 동작. 베타 초반엔 거의 안 모임

### AI로 목록 만들기

- LLM에게 "유명한 대학생 대외활동 목록"을 물으면 금방 나오지만, **없는 활동이나 끝난 기수를 지어낼 수 있다**
- → 후보를 뽑는 데만 쓰고, 넣기 전에 사람이 모집 공고로 하나씩 확인

### 정리

| 방법 | 장점 | 단점 | 제안 |
|---|---|---|---|
| **A. 팀이 직접 고른 목록 (seed)** | 정확. 우리 타겟에 맞는 것만. 분야·유형까지 같이 적을 수 있음 | 손이 감. 새 기수가 나오면 추가해야 함 | **쓴다.** 처음 100개 안팎 |
| **B. 사용자 등록 → 검수** | 쓸수록 늘어남. 우리가 모르는 활동도 들어옴 | 검수하는 사람이 필요. 중복·오타 | **쓴다.** A로 못 채운 것을 채움 |
| C. 공공 API 자동 수집 | 자동 | 맞는 API가 거의 없음 | 안 씀. 큰 봉사·축제 몇 개는 A에 손으로 |
| D. 대외활동 사이트 크롤링 | 제일 많음 | 팀 규칙 위반, 약관 위반, 민사 배상 사례 있음 | **안 함** |
| E. 대외활동 사이트와 제휴 | 정식으로 많이 받음 | 시간이 오래 걸림 | **문의 메일은 지금 보내 봄** |
| F. AI가 만든 목록 | 빠름 | 지어낼 수 있음 | A의 후보 뽑기에만 |
| G. 네이버 검색 API | 공식 API | 약관상 결과를 DB에 못 쌓음, 자동완성 API 없음 | 결과 없을 때 링크만 |
| H. 우리 사용자 활동명 모으기 | 외부 데이터 불필요, 5명 기준으로 개인 특정 방지 | 사용자가 쌓여야 함 | **나중에 추가** |

### 처음 목록 만드는 방법 (A)

1. **소윤이** 공유 시트 하나에 아래 칸으로 적는다

   | 칸 | 예 | 설명 |
   |---|---|---|
   | 공식명 | 멋쟁이사자처럼 대학 | 모집 공고에 쓰인 이름 그대로 |
   | 주최 | 멋쟁이사자처럼 | |
   | 기수·연도 | 13기 / 2025 | 명세 1.8 `period` |
   | 별칭 (최대 3) | 멋사, 멋사대학 | **줄임말은 꼭.** 검색은 줄임말을 못 찾음 (4장) |
   | 분야 | 개발·IT | 9개 중 하나. 분야 추천에 씀 |
   | 유형 | 동아리·학회 | 7개 중 하나 |
   | 확인한 곳 | 모집 공고 주소 | 검수용. DB엔 안 넣음 |

2. 다 적으면 시트를 CSV로 내려받아 소윤이 스크립트로 Supabase에 넣는다 (`status = verified`)
3. 처음 목표: **유형별 10~20개, 합쳐서 100개 안팎**. 인터뷰 A~G와 테스트 카드 20장에 나온 활동부터

### 기수(회차)는 어떻게 저장하나

명세: "같은 활동도 회차마다 따로" (기수마다 다른 행)

| 방법 | 장점 | 단점 |
|---|---|---|
| a. 기수마다 행 하나 (명세 그대로) | "13기"끼리 정확히 묶임 | 검색 결과 5개가 "13기, 12기, 11기…"로 같은 활동만 채움. 기록 수도 기수별로 쪼개져 5개를 못 넘김 |
| b. 활동 하나 + 기수는 기록에 따로 | 검색이 깔끔. 기록 수가 모임 | 명세와 다름. 기록에 기수 칸 추가 필요 |
| **c. a로 저장하되 검색 결과는 활동별로 묶어서** 최신 기수 하나만 보여주고, 고른 뒤 기수 선택 | 명세 유지 + 검색 깔끔 | 화면에 "기수 고르기"가 하나 더 생김 (디자인 확인 필요) |

→ 제안: **c**. 기록 수(5개 넘으면 표시)는 **활동 전체 기수 합**으로 센다.
→ ⚠️ 화면에 기수 고르는 칸이 생기는지 **명금·하영 확인 필요**.

## 4. 검색 방법

로컬에서 확인한 것 (11/16):
- pg_trgm은 한글도 글자 조각(trigram)으로 잘 쪼갠다 (`show_trgm('취업박람회')` → 6개)
- 하지만 **줄임말은 못 찾는다**: `similarity('과학기술준비위원회', '과준위')` = 0.08. → 줄임말은 별칭(`aliases`)에 넣어야 찾힌다
- 2글자 검색(`'%과준%'`)은 인덱스를 못 타고 전체를 훑는다. 수백 개라 문제없음

| 방법 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| **A. 포함 검색 + pg_trgm 정렬** | 이름+별칭을 소문자·띄어쓰기 없앤 글자에서 `like '%검색어%'`로 찾고, 앞부분 일치 → 비슷한 정도(`similarity`) 순 | 이미 만든 인덱스·함수 그대로. 추가 설치 없음. 로컬과 Supabase가 같음. 결과가 예측 가능 | 오타는 못 찾음 ("박람희") |
| B. A + 오타 허용 | 포함 검색 결과가 0개면 `word_similarity`가 일정 이상인 것도 보여줌 | 오타·일부 순서 바뀜도 찾음 | 엉뚱한 결과가 섞일 수 있음. 기준값을 맞춰야 함 |
| C. PGroonga 확장 | 한중일 글자에 맞춘 검색 확장 (Supabase에서 켤 수 있음) | 한국어 검색 품질이 제일 좋음 | 로컬 Docker 이미지에 없어서 따로 설치해야 함. 수백 개 규모에는 과함 |
| D. Postgres 전문 검색 (tsvector) | 단어 단위 검색 | 기본 기능 | **한국어 형태소 분석기가 기본으로 없음.** "박람회"와 "취업박람회"를 다른 단어로 봄 |
| E. 외부 검색 서비스 (Algolia, Meilisearch 등) | 별도 검색 서버 | 오타·초성 등 기능 많음 | 서비스 하나 더 운영. 데이터 동기화 필요. 과함 |
| F. 임베딩 검색 (BGE-M3) | 활동명을 벡터로 바꿔 비슷한 것 찾기 | 뜻이 비슷한 것도 찾음 | 키 입력마다 임베딩 호출(0.3초 안에 어려움). "이름 찾기"엔 오히려 부정확 |
| G. 네이버 등 외부 자동완성 | 글자 칠 때마다 외부 검색 | — | 공식 API 없음, 결과 저장 불가 (3장) |

**초성 검색** (나중): 이름의 초성만 뽑은 칸을 하나 더 두고 같은 방식(A)으로 찾으면 됨. 지금은 안 만듦.

## 5. 새 활동 등록 규칙

| 항목 | 선택지 | 제안 |
|---|---|---|
| 중복 | (a) 막지 않음 (b) 비슷한 이름이 이미 있으면 "혹시 이거예요?"로 기존 것 보여줌 | **(b)** — 검색에서 못 찾고 등록하는 경우가 많을 것. 응답에 후보만 같이 주고, 그래도 등록하면 등록 |
| pending 활동이 누구에게 보이나 | (a) 만든 사람만 (b) 아무에게도 안 보임 | **(a)** — 만든 사람의 검색 결과에는 나오게 (같은 활동을 또 등록하지 않게) |
| 하루 등록 수 제한 | (a) 없음 (b) 하루 N개 | 베타라 **(a)**. 문제 생기면 추가 |

계속 관리하기:
- **새 기수**: 사용자가 "새 활동 등록"으로 올리면 검수 때 기존 활동의 새 기수로 붙임
- **검수**: **소윤**이 Supabase 대시보드에서 `status`를 `verified`로 바꾸는 것으로 시작. 7일 안에 (CLAUDE.md 6장)
- **검수 기준** (제안): 2장의 "넣음" 조건에 맞는지, 모집 공고로 실제 있는지 확인, 이미 있는 활동이면 합침, 학교 이름이 들어가면 `verified`로 안 올림

## 6. 분야 추천 방법

활동명만 보고 9개 중 하나 고르기. 2단계 화면이 열릴 때 바로 보여야 하므로 **빨라야** 하고, 틀려도 사용자가 다른 걸 누르면 되므로 **완벽할 필요는 없다**.
보내는 것은 그 사람이 쓴 활동명뿐이라 POL-07(남의 반응·Q&A를 AI에 안 보냄)과 부딪히지 않는다.

| 방법 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| **① 공식 활동에 분야 저장** | `official_activity.genre` 칸 추가. 공식 활동을 고르면 그 분야 | 정확. 0초 | 공식 활동을 고른 경우만 |
| ② 같은 공식 활동 기록의 다수결 | 그 활동을 연결한 기록들이 고른 분야 중 제일 많은 것 | 데이터가 쌓이면 정확 | 처음엔 데이터 없음. ①이 있으면 필요 없음 |
| ③ 키워드 규칙 | "해커톤·개발" → 개발·IT, "카페·편의점·알바" → 서비스·응대 같은 사전 | 0초, 비용 없음, 결과 설명 가능 | 사전에 없는 이름은 못 맞춤. 사전 관리 필요 |
| **④ LLM 분류** | 활동명을 주고 9개 중 하나 고르게 (재현 서버 LLM 클라이언트 재사용) | 처음 보는 이름도 대체로 맞춤. 만들기 쉬움 | 1~3초. LLM 서버가 꺼지면 추천 없음 |
| ⑤ 임베딩 비교 | 활동명 벡터와 분야 9개 설명 벡터를 비교해 제일 가까운 것 | LLM보다 빠름(수십 ms). 재현 임베딩 재사용 | 짧은 이름에선 정확도가 들쭉날쭉. 분야 설명 문장을 다듬어야 함 |
| ⑥ 외부 검색 API + LLM | 네이버 검색 등으로 활동 설명을 찾아 LLM에 | 잘 모르는 활동도 설명을 보고 맞춤 | 외부로 사용자 입력이 나감. 느림. 약관 문제 (3장) |

**제안: ① → ④ 순서로, 둘 다 안 되면 추천 없음**
1. 1단계에서 공식 활동을 골랐고 그 활동에 분야가 있으면 → 그 분야 (즉시)
2. 아니면 LLM에 활동명만 보내 분류. **같은 이름은 결과를 저장해 두고 다시 안 물음**. 2초 안에 안 오면 포기
3. 실패하면 추천 칩을 안 보여줌 (화면은 그냥 분야 9개)

- 앱은 1단계에서 "다음"을 누르는 순간 요청을 보내 두면, 2단계가 열릴 때쯤 결과가 와 있다
- ⑤ 임베딩은 LLM이 느리거나 자주 실패하면 대신 쓸 후보. 실제 활동명 20~30개로 ④·⑤ 정확도를 비교해 보고 정한다 (실험 필요)
- 엔드포인트: `POST /activities/suggest-genre` `{ "activity_name": "...", "official_activity_id": "uuid" | null }` → `{ "genre": "행사 운영" | null, "source": "official" | "ai" | null }`

## 7. 바뀌는 DB

- `official_activity`에 `genre`(분야), `type`(유형) 칸 추가 (비어 있어도 됨)
- 기수를 c 방식으로 묶으려면 같은 활동의 기수들을 이어 줄 칸 하나 (예: `series_key` = 공식명을 정리한 글자)
- 분야 추천 결과 저장 테이블 (활동명 → 분야). 서버만 씀
